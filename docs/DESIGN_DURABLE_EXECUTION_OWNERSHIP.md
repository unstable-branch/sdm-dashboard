# Durable Execution Ownership — Design (rev 6)

Status: design only. No migration or production code is authorized by this document.
Baseline: origin/dev `df7a5f9` (PR #97, Phase 2 canonical model inputs integrated).
Rev 6 scope: addresses review round 5 blockers (task comment 17): (1) the claim protocol becomes a fenced append-only **generation log** — the exclusive creation of the next generation directory is the shared CAS for *every* claim mutation (spawn record, terminal write, takeover), there is no permanent lock to strand, stale-holder recovery is ABA-free by construction (a resurrected holder can only attempt an already-existing generation and loses the EEXIST race), and the spawn path re-reads the log and proves it still owns the current generation immediately before the side effect; (2) `owner_rebooted` is no longer licensed by the R exit hook alone — boot-liveness is a *platform-verified container-lifetime chain* (init/tini or R-as-PID-1 topology, self-verified at boot via `/proc`, announced as `pid_chain_verified`, with an API-side dual-boot liveness conflict guard), and any unverified prior-boot evidence yields a quarantined `owner_rebooted_unverified` state that never authorizes a replacement spawn.
Rev 5 scope: addresses review round 4 blockers (task comment 16): a no-gap, generation-checked stale-claim takeover that leaves a non-spawnable marker continuously visible (the public claim directory is never absent); one executable reserved-cancel transaction (direct `reserved → cancelled` CAS, no attempt exists to finalize, explicit concurrent-dispatch ordering); an execution/project-scoped internal authorization model that distinguishes request-driven actors (current-principal project-membership rechecks by the API, claim `owner_user_id` demoted to audit provenance) from a narrowly scoped service reconciler (observe/cancel only, never dispatch) so authorized collaborators and post-owner-deletion reconciliation both work; and the owner-restart constraint that a running child can only ever be present on the boot that spawned it (exit-hook invariant), so present-after-boot-loss is terminal-or-provably-dead evidence and no cross-boot ownership transfer exists.
Rev 4 scope: addresses review round 3 blockers (task comment 15): an executable idempotency-reservation transaction (pre-allocated run UUID + deferrable FK); atomically published owner-bound claims with one unambiguous takeover postcondition; execution-scoped internal-only Plumber operations re-authorized against current Hono project membership at every step; immediate-before-spawn payload/authority revalidation; attempt-canonical ownership (execution owner columns removed) with an explicit `accepted|adopted → lost_response` path; and queue removal moved out of the PostgreSQL transaction (post-commit, idempotent).
Rev 3 scope (retained): addresses review round 2 blockers (task comment 14): lost-response probe ordering and durable cancel intent; atomic Plumber claim creation/reclaim; persisted acceptance-time owner generation (boot identity); current-principal resolve authorization; conflict-safe request idempotency with non-reuse tombstones; complete PID-authority inventory including status liveness and shutdown; complete schema fields and valid allocation transactions. Also corrects a source-truth error from rev 2 (`input_assets.content_sha256` already exists).
Scope owner: REVIEW_LEDGER P2-10, P2-11; ROADMAP stage 5 ("Design and independently review the run/execution/attempt contract before migrations").
Do-not-claim: multi-replica safety (P2-10 exit criteria keep the single-replica limit until green); Targets enablement (P2-09 deferred).

## 1. Current state (verified against source)

### 1.1 What exists

- `runs` is a flat table with a lifecycle enum (`queued|running|completed|failed|cancelled`) plus two foreign job pointers: `jobId` (Plumber job id) and `bullmqId` (BullMQ job id). (`api/src/db/schema.ts:96-134`)
- Submission creates the run row first, then dispatches. Async path: insert `queued` run, then enqueue (`api/src/routes/sdm-runs.ts:88-156`). Sync path: insert a run already marked `running`, then call Plumber (`sdm-runs.ts:159-221`).
- The worker marks the run `running`, calls `client.runModel(payload)` — the side-effecting spawn — and only afterwards records the returned `job_id` (`api/src/services/queue-model-worker.ts:42-85`).
- Plumber generates `job_id = "run-<timestamp>-<4 random digits>"` (`plumber/R/helpers/models_helpers.R:157`), spawns a callr child, registers it in the in-process env `sdm_process_registry` (`models_helpers.R:1,259`), and writes `process_pid` into `meta.json` (`models_helpers.R:268`). The registry (and the child) live inside the Plumber container/process, not the queue worker.
- Cancellation: Hono discards/removes the BullMQ job, calls Plumber cancel (`sdm-runs.ts:418-450`); Plumber kills via registry handle first, then falls back to `process_pid` from `meta.json` (`plumber/R/helpers/plumber_helpers.R:151-186`), plus a Redis cancel flag keyed by job id with 1h TTL (`plumber/R/redis.R:98-116`). The model cancel handler *also* calls `sdm_kill_pid(meta$process_pid)` directly when the registry kill reported no kill (`models_helpers.R:1345-1347`).
- **Model job status treats a PID as liveness**: when the registry entry is gone, `handle_*_status` probes `meta$process_pid` with `pskill(pid, 0)` and reports "running" if any process with that PID exists (`models_helpers.R:802-813`). After an owner restart with PID reuse this is a stale-liveness bug, the status twin of the P2-10 cancel bug.
- **Plumber shutdown sweeps PIDs**: the `pr_hook(pr, "exit", ...)` handler kills every registry child, then iterates *all* job dirs and `pskill`s each `meta.json` `process_pid` for status `running` (`plumber/R/run_server.R:340-355`). Same stale-PID hazard at shutdown. `run_server.R` also owns the postroute replica-id header (`:243-253`) and is where a boot announce would live; rev 2 wrongly excluded it from the slices.
- Plumber auth: every protected call carries a verified principal — `X-Hono-Internal` + `X-Forwarded-User`/`Role` from the API (`api/src/services/plumber.ts:155-183`; `plumber/R/run_server.R:186-202`), or a direct API key — and job reads authorize **before** returning any domain error or metadata-derived status (`sdm_verify_run_owner`, `models_helpers.R:787-789`). This is the pattern the resolve endpoint must follow; key possession alone is not authorization.
- **Asset content identity already exists**: `input_assets.content_sha256` / `content_size` (`api/src/db/schema.ts:256-257`, migration `0038_input_assets.sql:48`), and current asset resolution *verifies* identity by re-hashing at resolve time (`matchesContentIdentity`, `api/src/services/input-assets.ts:267-277`). Rev 2 wrongly proposed these as new S1 columns; S1 adds no asset column — only constraints on their use for dispatch sealing (§2.2.1).
- Reconciliation is a 5s sweep: stuck-queued runs failed after 5 minutes (`api/src/services/plumber-sync.ts:88-113`), running runs polled by `jobId` (115-549), 404-streak runs failed as `PROCESS_CRASH` (446-547), stalled runs failed after 2h (123-147).
- Events are an in-process EventEmitter plus fire-and-forget Redis pub/sub with `_originPid` as the only origin marker; no event identity, no sequence (`api/src/services/job-events.ts:40-77`).
- `enqueueSdmJob` computes a deterministic BullMQ job id from `species|modelId|occurrenceAssetId|configHash|type` (`api/src/services/queue.ts:407-416`) and treats duplicate-id errors as success (399-403).
- `api/src/services/model-payload.ts` builds and *resolves* the model payload (safe-config projection, typed asset resolution to local paths: `buildModelPayload` :46, `resolveModelPayload` :199, `resolveModelInputAssets` :147). It defines **no** canonical serialization and **no** hash function, and its resolved asset values are mutable filesystem locators. A stable payload identity function must be *added*, not reused (§2.2.1).

### 1.2 Failure modes this design must close (with evidence)

1. **Duplicate-compute on lost response (P2-11).** If `runModel` succeeds server-side but the response is lost (proxy timeout, socket drop), the worker throws, the run is marked failed (`queue-model-worker.ts:52-71`), and the generic catch in `queue.ts:244-291` re-throws on string-matched "timeout"/"500"/"ECONNREFUSED" so BullMQ retries (attempts 2, `queue.ts:380`) — spawning a second R process while the first still runs. Plumber has no idempotency input, so it cannot tell a replay from a new dispatch (`models_helpers.R:157`).
2. **Transport retry replays a mutation.** The retry decision is string matching on error text (`queue.ts:281-283`), not on a durable reservation state.
3. **Stale-PID cancellation and stale-liveness status (P2-10).** Four distinct PID authorities exist today: the cancel fallback (`plumber_helpers.R:174-183`), the direct `sdm_kill_pid` in model cancel (`models_helpers.R:1345-1347`), the status liveness probe (`models_helpers.R:809-813`), and the shutdown sweep (`run_server.R:340-355`). After an owner restart with PID reuse, any of them can attribute a live process to a dead job (or kill an unrelated process). Rev 2 only removed the first; all four must go for model jobs.
4. **Equal-PID identity.** Registry entries are process-local and die with Plumber; two containers can present the same PID to any PID-based check (P2-10 test list).
5. **Dedup swallows a run.** Two submits with identical config produce two `runs` rows; the second enqueue hits the deterministic BullMQ id and returns the *first* job's id (`queue.ts:399-403`), so the second run row is never processed and is later failed by the stuck-queued sweep as `WORKER_ORPHAN` (`plumber-sync.ts:88-113`). The dedupe key omits `runId` (`queue.ts:414`).
6. **No reservation.** The run is durable but the dispatch is not: a worker crash between the `running` update and the Plumber call leaves a run with no `jobId` whose only recovery is the 10-minute orphan heuristic (`sdm-runs.ts:343-363`) — and that heuristic is per-request, so an unwatched run hangs until the 2h stalled timeout.
7. **Ownerless runs unmonitorable.** The sync sweep refuses runs without `parentRunId` (no durable creator binding) and skips them entirely (`plumber-sync.ts:150-162`).
8. **Event identity absent.** SSE/WebSocket consumers can observe duplicated or out-of-order states; nothing ties an emitted event to a durable transition.
9. **Status is ambiguous, not derived.** "running" on the runs row can mean reserved-but-never-dispatched, dispatching, accepted, or polling. "Unknown" currently licenses respawn (worker retry) — the exact inversion of the contract in `docs/ARCHITECTURE.md:54`.
10. **Lost submit response duplicates a logical submission.** No request-level idempotency exists anywhere in the submit path (`sdm-runs.ts:88-221`): a client that retries a POST after a lost 200 creates a second run and a second execution.

## 2. Contract

> Run: stable scientific result lineage and normalized specification. Execution: authorization and dispatch aggregate reserved before side effects; one execution is one authorized dispatch lineage with a bounded attempt sequence, and it is never reopened after it is finalized. Attempt: append-only invocation identity with its own external job identity; transport replays reuse an attempt, reconciliation probes the open attempt before replacing it. Owner: the Plumber instance *boot* that spawned and holds the child, identified durably at acceptance and verified inside its own namespace. Status is a projection of this history; unknown or accepted-but-unconfirmed is not permission to spawn again. (`docs/ARCHITECTURE.md:45-54`, restated as binding)

### 2.1 Run lineage and the terminal rule

- `runs` remains the scientific lineage: species, model, normalized config, provenance, metrics. It gains **no** attempt/dispatch columns. `runs.status` becomes a *projection* maintained only by the execution state machine; no other writer may set `status` once `executions` owns it (enforced by a single transition function, §3).
- **Executions are never reopened.** Once an execution reaches a terminal state (`succeeded|failed|cancelled|expired`) and `finalized_at` is set, it is immutable history. There is no reopen transition.
- **Authorized retry reserves a new execution.** `POST /runs/:id/retry` on a run whose latest execution is terminal (and whose inputs still resolve) creates a *new* execution row (`status=reserved`, new `nonce128`/`idempotency_key`, `retry_of_execution_id` set to the prior execution's id), subject to the same one-non-terminal-execution-per-run partial index. The prior execution and its attempts are untouched. Executions are numbered gaplessly per run via `run_seq` (§2.2.3 allocation); the API exposes the run-level attempt counter as `(run_seq, attempt_no)` pairs.
- Scientific results of a superseded execution are preserved on its attempts; retry never mutates them.

### 2.2 Durable reservation, request idempotency, and payload identity

New tables (design; exact SQL in the migration slice S1):

- `executions`: `id uuid pk`, `run_id fk`, `run_seq int not null` (gapless per run; allocation in §2.2.3), `status` enum (`reserved|dispatching|cancel_requested|accepted|lost_response|adopted|succeeded|failed|cancelled|expired`), `attempt_count int not null default 0`, `cancel_requested_at timestamptz null` (durable cancel intent, orthogonal to status — §2.4), `idempotency_key text not null unique` (dispatch-replay identity within this execution), `nonce128 text not null` (one-time 128-bit random value, hex, generated in the reserve transaction; input to `idempotency_key` and attempt keys, §2.2.4), `payload_hash text not null` (§2.2.1), `retry_of_execution_id uuid null` (self-FK to `executions.id`; set only by authorized retry, §2.1), `lease_expires_at timestamptz null`, `reserved_by_principal uuid not null`, `project_id uuid not null` (authorization scope for every downstream owner check), `created_at`, `finalized_at null`.
  - **No owner columns on the execution, and no `plumber_job_id`.** Ownership and external job identity are attempt-canonical: they live only on `execution_attempts` (below). Rev 3's execution-level `owner_instance_id`/`owner_boot_id` is withdrawn — it was written once at the initial dispatch but then also (contradictorily) updated at every acceptance, and a reconciliation attempt on a new boot would have had to overwrite it. Any "execution owner" is a *derived, explicitly mutable* projection = the owner snapshot of its latest non-final attempt; it is never stored and never used for routing (routing always uses the attempt's snapshot, §2.3).
- `execution_attempts` (append-only): `id uuid pk`, `execution_id fk`, `attempt_no int` (= the `attempt_count` value produced by the dispatch CAS; gapless, unique `(execution_id, attempt_no)`), `attempt_key text not null` unique (= `idempotency_key || ':' || attempt_no`), `kind enum(initial|reconciliation)`, `plumber_job_id text null` unique (external identity lives here, one-time write per attempt, §3 invariant 3), `owner_instance_id uuid null`, `owner_boot_id uuid null` (snapshot of the Plumber instance/boot that accepted *this* attempt; one-time write alongside `plumber_job_id`), `outcome text null`, `error_code text null`, `error_hint text null`, `started_at`, `finalized_at null`. **Partial unique index**: one non-final attempt per execution (`CREATE UNIQUE INDEX ... ON execution_attempts(execution_id) WHERE finalized_at IS NULL`).
- `idempotency_requests`: `key text not null`, `principal uuid not null`, `project_id uuid not null`, `request_hash text not null`, `run_id uuid not null unique`, `response_status int null` (null until the submit transaction commits; see §2.2.2), `response_body jsonb null`, `created_at not null`, `expires_at not null`. **Primary key `(principal, key)`**. Rows are **never deleted** — the tombstone outlives the replay window (§2.2.2 retention).
- `plumber_instances`: `id uuid pk` (the stable `SDM_PLUMBER_INSTANCE` identity, §2.3), `api_base_url text not null`, `first_seen_at`, `last_seen_at`.
- `plumber_instance_boots` (append-only; solves the destroyed-era problem): `boot_id uuid pk` (generated by the Plumber process at startup: uuid4; collision-safe, no clock ordering assumed), `instance_id uuid fk→plumber_instances`, `announced_at timestamptz not null`, `last_seen_at timestamptz not null`, `pid_chain_verified boolean not null default false` (the self-verified `/proc` process-chain assertion of the container-lifetime chain, §2.2.4 — gate for `owner_rebooted` vs `owner_rebooted_unverified` classification). One row per Plumber process start; prior boots are never overwritten and never updated except `last_seen_at`. "Current boot" for an instance = the row with the greatest `announced_at` (ties broken by `boot_id`; correctness never depends on tie order — any mismatch is owner-gone).
- `execution_events` (append-only, transitions only): `id bigserial pk`, `execution_id fk`, `attempt_no int null`, `seq int`, unique `(execution_id, seq)`, `event text`, `observed jsonb`, `emitted_at`. Progress logs/percent stay ephemeral (Redis + pub/sub); only state transitions are durable.
- **Deleted from rev 1:** `dispatch_instances` as the owner record. The queue worker still registers itself (lease heartbeats, single-replica lock), but it is explicitly **not** the compute owner; the owner is the `(plumber_instance, boot)` captured at acceptance.

#### 2.2.1 Payload identity (canonical hash)

The hash input is the **resolved canonical payload** with mutable locators replaced by content identity:

1. Start from the Phase 2 safe payload exactly as built by `buildModelPayload` (`model-payload.ts:46`): `{ modelId, species, config: <projected safe config> }`.
2. Replace each resolved asset reference (occurrence, climate, covariate paths produced by `resolveModelInputAssets`, `model-payload.ts:147`) with a content tuple `{"asset_id": <db id>, "content_sha256": <sha256 of the stored bytes>}`. **`input_assets.content_sha256` already exists** (`api/src/db/schema.ts:256`, migration `0038_input_assets.sql:48`) and resolution already revalidates identity against the stored bytes (`matchesContentIdentity`, `api/src/services/input-assets.ts:267-277`); S1 adds no asset column. Sealed dispatch requires the value to be present and *revalidated at reservation time*:
   - **Reservation-time sealing.** The submit transaction requires a non-null `content_sha256` for every referenced asset. `matchesContentIdentity` already re-hashes at resolve time; the submit path runs that same verification inside the reserve transaction. If an asset's stored hash is null (legacy rows predating Phase 2 identity), the reserve transaction computes it from the stored bytes and persists it (`UPDATE input_assets SET content_sha256=..., content_size=... WHERE id=? AND content_sha256 IS NULL`) before hashing the payload — a one-time lazy backfill, still inside the transaction. A hash mismatch (stored hash ≠ re-hashed bytes) fails the submit with `422 asset_identity_mismatch`; it is a read-side rejection, the asset's state is unchanged, and the mismatch is logged for ops. Identity is therefore *verified*, not "computed once".
   - The resolved filesystem path is *dispatch-time data*, never part of identity — the fix for the "resolved paths are mutable locators" finding.
3. Serialize with a new, single, exported `canonicalExecutionJson()` in `api/src/services/model-payload.ts`: deterministic JSON (object keys sorted lexicographically, no whitespace, no undefined keys, numbers via `String(n)`), defined once and unit-tested against fixtures. This function does not exist today and must be added; nothing else may implement payload serialization for identity purposes.
4. `payload_hash = sha256(canonicalExecutionJson(resolvedPayload))`. Two dispatches with the same `payload_hash` are byte-identical scientific inputs; the same hash never by itself authorizes dedupe of *distinct* runs (§4, rejected alternatives).

#### 2.2.2 Request-level idempotency (lost submit response)

Contract, end to end:

- **Key source.** The client sends an `Idempotency-Key` header (opaque, ≤128 chars) on `POST /runs` (and the sync variant). The reference web UI generates one per user-initiated submission attempt (uuid4 held in form state) and reuses it on any client-side retry of that logical submit. Server accepts only keys matching `^[A-Za-z0-9._-]{8,128}$`; missing key on the async POST is still allowed (existing clients) but marks the request non-replayable and is logged — the UI slice makes the key mandatory from its side.
- **Scope.** Uniqueness is `(principal, key)`: one principal's key cannot collide with another's, and a key is bound to the project of its first use (`project_id` recorded; a replay with a different project is a `409 key_scope_mismatch`).
- **Atomic lookup-or-create — conflict-safe reservation (rev 3's transaction was not executable; withdrawn).** The rev-3 draft made `run_id` `NOT NULL` but inserted the reservation without a run id and identified the winner via `RETURNING run_id IS NULL` — PostgreSQL would reject that insert before the branch. Rev 4 fixes the ordering and the constraint mechanics:
  - **Run UUID is allocated client-side (in the API, `randomUUID()`) before any SQL.** The reservation and the run row therefore share one known id from the start; `run_id` stays `NOT NULL`.
  - **The FK `idempotency_requests.run_id → runs.id` is created `DEFERRABLE INITIALLY DEFERRED`.** The reservation is inserted *before* the run row in the same transaction, so an immediate FK check would fail at that statement; the deferred constraint is checked at commit, when the run row exists. `SET LOCAL CONSTRAINTS ALL DEFERRED` inside the transaction is explicit in the implementation so the behavior does not depend on the migration's default.
  - **Transaction (all statements in one `BEGIN … COMMIT`):**
    1. `INSERT INTO idempotency_requests (principal, key, project_id, request_hash, run_id, expires_at) VALUES (?, ?, ?, ?, <pre-allocated run uuid>, now()+interval '48 hours') ON CONFLICT (principal, key) DO NOTHING RETURNING run_id;`
       - **A row returned proves we own the reservation**: `ON CONFLICT DO NOTHING` returns a row only to the single inserter that won the PK insert; every concurrent loser gets zero rows without error.
    2. **Row returned (winner)**: `SET LOCAL CONSTRAINTS ALL DEFERRED` is already in effect; `INSERT INTO runs (id, status, …) VALUES (<pre-allocated run uuid>, 'queued', …)`; `SELECT id FROM runs WHERE id=? FOR UPDATE` (the §2.2.3 run_seq lock, free on a fresh row); insert the execution (`reserved`, `nonce128`, `idempotency_key`, `payload_hash` from reservation-time sealing §2.2.1); compute the response body (`{runId, queuedAt}` — fully known before commit); `UPDATE idempotency_requests SET response_status=?, response_body=? WHERE principal=? AND key=?`; `COMMIT`. The deferred FK is satisfied at commit. **Any failure anywhere rolls the whole transaction back including the reservation — a failed submit can never poison the key, and a rolled-back reservation row simply never exists.**
    3. **Zero rows (loser — concurrent or replay)**: no run/execution side effects were created by us; `SELECT request_hash, project_id, run_id, response_status, response_body, expires_at FROM idempotency_requests WHERE principal=? AND key=?` and:
       - request_hash mismatch → `422 idempotency_key_reused_with_different_payload`, no side effects;
       - project mismatch → `409 key_scope_mismatch`;
       - `expires_at` passed (replay window closed) → `410 idempotency_key_expired` — **the key is never reusable**: the tombstone row persists, so a 410 can never fall through to creating a second execution;
       - `response_status IS NULL` (a reservation whose transaction is still in flight — the only way a committed row has no response) → `409 idempotency_key_in_progress` (retryable; the concurrent winner commits or rolls back and the next attempt takes the replay or fresh path). There is no other null-response state: rolled-back rows do not exist.
       - otherwise → return the stored `response_status`/`response_body` verbatim with `Idempotency-Replayed: true`.
  - Concurrency proof: a concurrent conflicting `INSERT … ON CONFLICT DO NOTHING` blocks on the in-flight uncommitted reservation (PostgreSQL speculative-insert wait) and returns zero rows only after the winner commits or aborts; the loser's follow-up `SELECT` therefore always sees either the committed row (replay branch) or nothing at all (the winner aborted → the loser's own insert already succeeded, i.e. it was not a loser). The PK `(principal, key)` plus `ON CONFLICT DO NOTHING` makes the reservation exactly-once under any interleaving; there is no lock-free window in which two logical executions exist for one key, and no failed-insert abort path.
- **Replay semantics.** A replay never re-enqueues BullMQ or touches Plumber. It returns the original response only.
- **Retention / non-reuse (rev-2 deletion withdrawn).** The replay window is `expires_at = created_at + 48h` (generous vs. UI retry windows). After expiry the row is a permanent tombstone: replays get `410`, and no future request with the same `(principal, key)` can create a second execution for that key, ever. To bound storage, the reconciler's housekeeping pass nulls out `response_body` for rows past `expires_at + 7d` (keeping `key`, `request_hash`, `run_id`, `response_status`) — the tombstone itself is retained indefinitely. This satisfies the ROADMAP one-key/one-execution gate: reuse after housekeeping is still a `410`, not a new run.
- **Integration tests (gate).** (a) Two concurrent identical POSTs with the same `(principal, key)` and payload → exactly one `runs` row, one `executions` row, one enqueue, both HTTP responses identical, the loser replaying. (b) Same key + mutated payload → `422`. (c) Cross-principal same key → two runs, both processed (keys are scoped). (d) Same key after `expires_at` → `410`, and a *new* run is still not created. (e) After housekeeping nulls `response_body`, the same key still returns `410`/replay-status and never creates a second execution. (Test 4a–e in §6.)

#### 2.2.3 Reservation protocol (dispatch side)

All steps inside the execution service; every numbered step is one transaction (or a CAS + transactional follow-up as written):

1. **Reserve** (in the submit transaction, §2.2.2): insert execution `status='reserved'`, generating `nonce128` (crypto-random 128-bit, hex) in this transaction and storing it on the row; `idempotency_key = sha256(canonicalExecutionJson({execution_id, payload_hash, run_seq, nonce128}))`. This key is *dispatch-replay* identity inside one execution; request-level replay is handled by §2.2.2, so deriving from a fresh execution id is harmless. `payload_hash` binds the reservation to the exact inputs it authorized (§2.2.1, reservation-time sealing).
   - `run_seq` allocation inside the same transaction: first `SELECT id FROM runs WHERE id=? FOR UPDATE` (explicit row lock on the run — this is the serialization point), then `SELECT COALESCE(MAX(run_seq),0)+1 FROM executions WHERE run_id=?` (plain aggregate; correctness comes from the runs-row lock, not from locking the aggregate), then insert the execution. For the submit path the run row was just inserted in the same transaction, so the lock is free; for the retry path (§2.4) the lock serializes concurrent retries of the same run. (Rev 2's `MAX(...) ... FOR UPDATE` recipe — locking a non-existent aggregate — is withdrawn.)
2. **Dispatch CAS + attempt allocation**: one transaction:
   `UPDATE executions SET status='dispatching', attempt_count = attempt_count + 1, lease_expires_at = now()+<lease> WHERE id=? AND status='reserved' RETURNING attempt_count;`
   then `INSERT INTO execution_attempts (execution_id, attempt_no, attempt_key, kind) VALUES (?, <RETURNED attempt_count>, <idempotency_key || ':' || attempt_count>, 'initial')`. `attempt_no` **is** the RETURNING `attempt_count` (rev 2's undefined `RETURNING attempt_no` is withdrawn). Gapless because only the CAS winner increments, and the increment is transactional with the attempt insert.
3. **Cancel checkpoint A (pre-call, combined with immediate-before-spawn revalidation).** The worker re-reads the execution row immediately before the Plumber call. If `status='cancel_requested'` or `cancel_requested_at IS NOT NULL` (or any terminal), the worker does not call Plumber; one transaction: finalize attempt (`outcome='cancelled'`), finalize execution `cancelled`. No spawn has happened, so nothing is orphaned.
   **Immediate-before-spawn revalidation (reservation-time sealing alone is not enough — review round 3).** In the same pre-call block the worker *re-resolves current authority and inputs* and compares against the reservation, preserving the existing Phase 2 boundary where the worker already re-resolves the principal and payload just before dispatch (`queue-model-worker.ts:27-31`):
   - re-resolve the current principal (`resolveCurrentPrincipal`) and current project membership/action scope;
   - re-resolve every referenced asset and re-run identity verification (`matchesContentIdentity`, `input-assets.ts:267-277`);
   - recompute the canonical payload hash (`canonicalExecutionJson`, §2.2.1) and compare with the execution's sealed `payload_hash`.
   Any failure — principal removed, membership revoked, project gone, asset deleted/quarantined, byte mutation, hash mismatch — denies the dispatch: execution → `failed` with `error_code='AUTHORIZATION_LOST'` (authority) or `'INPUT_MUTATED'` (hash mismatch, the `422 asset_identity_mismatch` analog), attempt finalized, no Plumber call. A revocation between reservation and dispatch therefore cannot spawn from stale locators.
   **What Plumber rechecks before reading:** the internal service token and execution-key signature (existing `plumber.ts:170-183` / `run_server.R` auth), the claim's owner binding (§2.2.4), and the registry liveness of its own child; Plumber does not recheck project membership — that is the API's check above, made immediately before the call.
4. **The worker then calls Plumber** `POST /models/run` with `attempt_key` in the body, under the service-internal execution-scoped call (§2.2.4 authorization). The Plumber claim protocol (§2.2.4) makes the spawn idempotent per attempt key.
5. **Cancel checkpoint B (post-response).** On 200: one transaction:
   CAS `UPDATE executions SET status='accepted' WHERE id=? AND status IN ('dispatching','cancel_requested')` — preserving `cancel_requested_at` in every case (intent is never erased by a status transition; there is no branch that clears it). **Owner identity is written only on the attempt** (attempt-canonical ownership, §2.2 schema): `UPDATE execution_attempts SET plumber_job_id=?, owner_instance_id=?, owner_boot_id=? WHERE execution_id=? AND attempt_no=? AND plumber_job_id IS NULL` (one-time write). If `cancel_requested_at IS NOT NULL`, immediately route cancel to the owner (§2.4). Because the child is discoverable by `attempt_key`, adopt-and-cancel is always possible even if this worker dies between response and checkpoint: the reconciler key-probe finds it.
6. **Outcomes:**
   - 200 + `job_id` + `owner`: execution → `accepted` (checkpoint B), attempt carries the external identity and owner snapshot. A 200 with no `owner` object is a contract violation: nothing is written; execution → `lost_response` (the child may exist and is found by the probe path).
   - Explicit application rejection (4xx with a body): finalize attempt `failed`, execution `failed`; no automatic retry.
   - **Transport failure (no response): execution → `lost_response`, the attempt stays open** (its `plumber_job_id`/owner columns remain null; nothing may write them except a probe-adoption or checkpoint B). The reconciler probes **before finalizing** (this ordering is the rev-2 blocker-1 fix):
     a. **Probe the open attempt first**: `GET /models/resolve?key=<attempt_key>`.
        - **Present** (`present` with `job_id`, running or terminal): CAS execution `lost_response→adopted`; write `plumber_job_id` + owner columns on the still-open attempt (one-time write — allowed because the attempt is not finalized yet; invariant 2 permits exactly this and no later write); then project the observed Plumber status: terminal outcome finalizes attempt and execution accordingly; still-running leaves the attempt open under `adopted` and the normal owner-routed poll takes over. **Running-present evidence can only come from the boot that spawned the child** (the registry is process-local, §2.3, invariant 14); a key-probe that returns running-present therefore implies that boot is still live, and polling continues through it. If `cancel_requested_at` is set, route cancel to the owner immediately after adoption (durable intent survives the whole path).
        - **`claimed` / `claimed_not_spawned` with a live, fresh claim on its *owning* boot** (claim's recorded `boot_id` equals the responding process's boot, no confirmed child, within the stuck threshold): wait; re-probe next sweep. **A non-terminal claim whose recorded `boot_id` is not the responding process's boot is dead only under the verified container-lifetime chain (§2.2.4, invariant 14): a *verified* prior boot (`pid_chain_verified: true` announced by that boot, no `instance_conflict`) returns `owner_rebooted`, confirmed absence — finalize the open attempt (`outcome='unknown'`, `error_code='OWNER_RESTART'`), then the reconciliation attempt or `expired` per budget; it never waits and never transfers the child across boots. An *unverified* prior boot (`pid_chain_verified: false`, or `instance_conflict` detected) returns `owner_rebooted_unverified`: the reconciler finalizes the open attempt (`outcome='unknown'`, `error_code='OWNER_RESTART_UNVERIFIED'`) and finalizes the execution `failed` (quarantined for ops — unknown is not permission to spawn); **no replacement attempt is ever allocated from unverified evidence**; ops may confirm death out-of-band and authorize a normal retry, which is a fresh execution under §2.1. A current-boot claim past the stuck threshold with no live registry entry is taken over by Plumber under the fenced generation-log takeover protocol (§2.2.4); **`taken_over` is itself confirmation of absence** (takeover only happens when no registry entry and no terminal dir exist), so the probe treats it like the `not_found` path: finalize the open attempt (`error_code='LOST_RESPONSE'`), then the reconciliation attempt or `expired` per budget. The replacement attempt's fresh key is unaffected by the terminal takeover claim.
        - **`not_found` (confirmed absence — no public claim dir at all)**: only now finalize the open attempt (`outcome='unknown'`, `error_code='LOST_RESPONSE'`), then, subject to the reconciliation budget (§8.5), allocate exactly one `reconciliation` attempt: dispatch CAS (`UPDATE executions SET status='dispatching', attempt_count=attempt_count+1 WHERE id=? AND status='lost_response' RETURNING attempt_count`), insert attempt `kind='reconciliation'`, and proceed through steps 3–5 (including the immediate-before-spawn revalidation of step 3). Budget exhausted → finalize execution `expired`.
   - BullMQ job options change to `attempts: 1`. The string-matched re-throw (`queue.ts:281-283`) is deleted. A failed BullMQ job leaves the execution in its last durable state for the reconciler.
   - **`accepted|adopted` → `lost_response` (the explicit owner-loss transition, previously missing):** when an owner-addressed poll/cancel returns `owner_gone`, the execution keeps its `accepted|adopted` status while the reconciler key-probes the open attempt by `attempt_key` (§2.5). The probe after owner loss can return only terminal or dead evidence — **there is no "resume polling through the current boot" for another boot's child, and none is needed**: a running child is live only on the boot that spawned it (invariant 14), so running-present evidence would contradict the owner-gone trigger. Probe outcomes: terminal-present → adopt/write identity if missing and finalize with the observed outcome (no status change past terminal); probe confirmed absent (`not_found`, `taken_over`, or verified `owner_rebooted`) → finalize the open attempt (`outcome='unknown'`, `error_code='OWNER_GONE'` — or `OWNER_RESTART[_UNVERIFIED]` with the execution quarantined per the unverified path above where the container-lifetime chain does not verify), then CAS `accepted|adopted → lost_response` in the same transaction as the attempt finalization, and continue with the reconciliation-attempt-or-expired path of step 6 (the replacement attempt, if budgeted, is dispatched fresh on the current boot and records its *own* owner snapshot; the finalized attempt's snapshot is never rewritten — invariant 12). This transition is drawn in §3.

The partial unique index (one non-final attempt per execution) is exactly what makes the ordering above implementable: the open attempt is the probe target and the adoption write target while it exists, and its finalization is the gate that permits the reconciliation attempt insert.

#### 2.2.4 Plumber key-claim protocol (atomic, replay-safe, authorized)

Plumber-side contract changes (slice S2: `models_helpers.R`, `plumber.R`, `plumber_helpers.R`, and `run_server.R` for announce/shutdown, §7):

- **Authorization model (binding, review rounds 3+4): execution-scoped, internal-only, two actor classes.** `POST /models/run`, `GET /models/resolve`, and claim-bound status/cancel reads are **not reachable by external API keys**. Every claim-bound call requires the internal service token (`X-Hono-Internal`, `plumber.ts:155-169`) *plus* the execution-key signature headers (existing `executionHeaders`, `plumber.ts:170-183`, an HMAC over the exact `execution_id`) *plus* an actor assertion. **Plumber never derives project authorization itself** — it holds no membership data; the claim's `owner_user_id` is audit provenance only, never an authorization check. The two actor classes:
  - **Request-driven actor** (a user's resolve/replay/poll/cancel/dispatch): the API forwards the *current verified principal* (`X-Forwarded-User`/`Role`) and has — in the same request, immediately before the Plumber call — rechecked that principal's **current project membership and action scope against the execution's `project_id`** (the same route-level guard family the run/cancel/retry routes already perform, e.g. the `sdm-runs.ts` project guards, plus the current-principal re-resolution the Phase 2 worker already does before dispatch, `queue-model-worker.ts:27-31`). Any current project member with action scope passes — not just the historical owner. A foreign-project principal, removed membership, or deleted user fails the API recheck and **no Plumber call is made at all**: the API returns `404 {run not found}`-shaped responses indistinguishable from a missing execution, disclosing nothing.
  - **Service reconciler actor**: the API's own reconciler calls with the internal token + execution signature + `X-SDM-Actor: service` (included in the signed header set, so it cannot be forged without the execution key) and *no* forwarded user principal. Plumber grants this actor **observe (resolve/status) and cancel on the bound execution only — never dispatch/spawn** (`POST /models/run` requires a forwarded human principal unconditionally). Service-actor calls are audit-logged. This is what makes post-owner-deletion reconciliation legal: the reconciler never re-resolves the dead reserving principal, and never re-dispatches on their behalf.
  - Plumber verifies per call: internal token present; execution signature valid and its `execution_id` equals the claim's `execution_id` (key possession alone is never enough); actor is a forwarded principal or the signed service actor. Direct external API-key access to any claim-bound route → `401` with zero disclosure (plumber-auth-contract suite pins this). `sdm_verify_run_owner` authorize-before-disclose remains the last line for any route the migration has not yet converted.
  - **Service reconciliation when the reserving user is gone**: if `resolveCurrentPrincipal(reserved_by_principal)` fails or the user's membership in `project_id` has been removed, the reconciler does **not** keep dispatching on that user's behalf. A reserved/not-yet-accepted execution is finalized `cancelled` with `error_code='AUTHORITY_REVOKED'`; an accepted/adopted execution is observed to completion and cancelled when requested **through the service actor** (its spawn already passed the immediate-before-spawn revalidation, §2.2.3 step 3). Dispatch/re-dispatch always requires a live human principal passing the request-driven recheck — the reconciler never spawns.
- **Claim primitive — staged atomic publication of generation 0.** `sdm_claim_attempt_key(key, owner_user_id, project_id, execution_id, boot_id)`:
  1. The claim is *staged* under a private namespace: `dir.create(file.path(app_dir, "outputs", "claims", ".staging", paste(digest(key), uuid, sep="-")), showWarnings=FALSE)` — a directory *no public lookup ever reads*. The winner writes the **complete owner-bound** generation-0 claim there (`{key, claimed_at, owner_user_id, project_id, execution_id, boot_id, generation: 0, state:"claimed"}` — all authorization anchors and the boot binding present before anything is public), fsyncs it as `claim.json`, then **publishes with one atomic rename**: `file.rename(<staging dir>, file.path(app_dir, "outputs", "claims", digest(key)))`.
     - rename succeeds → the key is now publicly claimed, and **there is no public window in which the claim dir exists without a complete, owner-bound `claim.json`**: readers see either no dir (`not_found`) or the complete file.
     - rename fails (EEXIST/ENOTEMPTY — another process published first) → the loser **removes its own staging dir**, then takes the read-and-authorize path. Publication is the CAS; two publishers cannot both win.
  2. **Every subsequent mutation is an append to a fenced generation log (the rev-5 overwrite-in-place shape is withdrawn).** The claim directory `outputs/claims/<digest(key)>/` holds an append-only sequence of generation directories: `g0/claim.json` (the published claim above, renamed in place from staging as a whole directory) and, for every later mutation, `g<k>/` created **exclusively** — `dir.create(file.path(claim_dir, paste0("g", k)), showWarnings=FALSE)` is the shared CAS for *all* claim mutations: the pre-spawn spawn record, terminal-state writes, and stale-claim takeover all use the same primitive:
     - **Exactly one mutator wins generation k**: exclusive create succeeds for exactly one caller; every concurrent or resurrected latecomer gets EEXIST, re-reads the log, and treats the winner's generation-k content as current state. This closes the ABA class by construction: generations are monotone and created once; a stale holder that recovers can only ever attempt a generation that already exists, and it loses the EEXIST race deterministically. No lock file exists to strand or be recovered ambiguously.
     - The winner writes the **complete** claim object (full state, carried forward from the generation it read) into `g<k>/claim.json` via temp-file + rename *inside its exclusively-owned generation dir* (only the winner writes there), fsyncs, then the mutation is **committed** — the existence of `g<k>/claim.json` is the commit record. The winner then performs the operation's post-commit effects (spawn, forensics, quarantine), which are idempotent and retryable because the generation log never rolls back.
     - **Reader protocol**: current claim = the highest `g<k>/claim.json` that parses. A `g<k>` dir with no readable `claim.json` is *pending*: readers use the previous generation and never block. Pending generations only exist while their exclusive winner is mid-write or has crashed mid-write (crash recovery below).
     - **Crash recovery of a pending generation (no lock, no ABA)**: a `g<k>` dir with no readable `claim.json` whose winner is provably unable to finish — the claiming holder's `boot_id` is not the current boot (§2.2.4 boot-liveness), or the pending dir is older than the stuck threshold (10 min; a live winner's write window is milliseconds, so an old pending dir is a crash by any reasonable standard) — is **abandoned** by a single recoverer via an exclusive marker `dir.create(g<k>/.abandoned)` (EEXIST means someone else abandoned it first; both proceed to the next step, which is itself the exclusive-create CAS, so at most one recoverer appends the *next* generation). Readers skip abandoned generations. **The recoverer's own append must pass the pre-spawn fence below if it spawns** (it never does — takeover quarantines rather than spawns); recovery of a pending generation only ever completes state, never side effects: the crashed winner's spawn intent dies with its generation.
     - **Hazard note (crash between side effect and registry insert, stated honestly):** if the dispatcher crashes after appending its spawn record and after spawning the callr child but before inserting the registry entry, the child exists untracked. The claim's spawn record (with `job_id`) is durable; after the stuck threshold it is takeover-eligible; takeover quarantines the referenced job dir and the key can never spawn again. The untracked child is not killable through the registry, but it cannot outlive the container-lifetime chain (invariant 14: its supervisor namespace died or dies with the boot that spawned it) and is swept by `orphan_cleanup`'s stale-running marking at the next boot. No design path can double-spawn it, because every spawn requires the pre-spawn fence below and the key is generation-fenced.
  3. **The pre-spawn fence (the side effect is authorized only by the current generation, proven immediately before it).** The dispatch handler's sequence, in order:
     a. Read the log; current generation is `g` with the dispatcher as claim holder.
     b. Append generation `g+1` = the spawn record: `{state:"spawned", job_id, holder_boot_id, holder_uuid, ...}` (the spawn intent is durable before any side effect — the crash table's `claimed_not_spawned` row exists precisely because this record can outlive the spawn).
     c. **Immediately before the callr spawn (the side effect), re-read the log and verify**: current generation is `g+1`; its `claim.json` is *this process's own* spawn record (`job_id` matches, `holder_boot_id` is this boot, `holder_uuid` matches); **no generation `g+2` or higher exists**. Any mismatch (a takeover or terminal write advanced the log, or this record was quarantined) aborts the spawn with the takeover/terminal response — the dispatcher never spawns from a stale generation.
     d. Spawn the child, insert the registry entry, return `{job_id, owner}`.
     Within one boot this fence is airtight by construction, not just by re-read ordering: plumber is single-threaded (one R process serves requests sequentially; `run_model_background` returns immediately via callr), and the takeover sweep (`orphan_cleanup` extension) runs **at boot only** (`run_server.R:288` is startup-time today and stays startup-time for the claim sweep) — so a sweep can never interleave between steps (c) and (d) of a live dispatch request in the same process. The re-read in (c) is nonetheless mandatory and is what closes the *cross-boot* case: a dispatcher that recovered from a long stall, or a claim written by a prior boot whose container-lifetime chain permits takeover, must prove its record is still current. The only interleavings that can beat the re-read are ones where the dispatcher's own boot is dead — which the container-lifetime chain (invariant 14) already excludes.
     **Corollary — no mutation is ever performed without the append CAS:** replay that observes `claimed_not_spawned`/`taken_over` states never overwrites the log; it only reads it. The rev-5 "atomic replace of claim.json behind a `.takeover` lock" is withdrawn (see §4).
  4. **Unreadable/corrupt `claim.json` in the current generation** (should be impossible under the protocol; treated defensively): resolve cannot authorize against it, so it **discloses nothing** — authorized callers get `404 Run not found` (fail-closed, indistinguishable), the condition is logged for ops, and the claim is takeover-eligible on the stuck threshold (its pending-generation recovery path applies).
- **Claim content.** Each generation's `claim.json` = `{key, claimed_at, generation, state: "claimed"|"spawned"|"taken_over"|"terminal", owner_user_id, project_id, execution_id, boot_id (the spawning process's boot uuid, recorded at generation 0 and never changed), holder_boot_id, holder_uuid (the mutator identity for the generation — this boot's uuid plus a per-mutation uuid), job_id (once generated, before spawn), taken_over_by_boot, taken_over_at (takeover only), finished_at (terminal only)}`. `boot_id` is how resolve distinguishes "fresh claim, wait" from "prior boot's child — classify per the verified container-lifetime chain" (invariant 14). `generation` is the log position: monotone, one exclusive create per integer, and the fence every mutator must re-read (the pre-spawn fence above) before a side effect.
- **Crash-point table (all persisted states are replay-safe; resolve states are exact; every state below discloses only after current-principal authorization passes):**
  | Crash point | Durable evidence | Resolve-by-key returns | Reconciler action |
  |---|---|---|---|
  | before claim publish | staging dir only (private) | `not_found` | lease expiry → (finalize attempt if open) → reconciliation attempt |
  | claim.json write crashed pre-publish | staging dir only | `not_found` (same as above; no public state existed) | as above; staging dirs are swept with `orphan_cleanup` |
  | after publish (`claimed`), before spawn record | `g0/claim.json`, `state:'claimed'`, no `job_id` | `claimed` | same boot + fresh → wait; prior boot → classification below; same boot past threshold → fenced takeover (below) |
  | spawn record appended, crash before spawn (pending registry absent, no side effect) | `g<k>` spawn record with `job_id`, no registry entry, no terminal job dir | `claimed_not_spawned` (same boot, fresh) / `owner_rebooted`|`owner_rebooted_unverified` (prior boot, per the verified chain, below) | same boot: wait or fenced takeover; prior boot: per classification below |
  | after spawn, before response reached worker | registry entry + spawn record | `present` (+ status) | adopt (→ `adopted`), §2.2.3 step 6a |
  | after terminal completion | terminal job dir + terminal generation record | `present` (terminal status) | adopt + finalize with observed outcome |
  | owner restart before terminal (container-lifetime chain: child killed by namespace teardown, no terminal write) | spawn record with `job_id`, prior `boot_id`, no registry entry, no terminal dir | `owner_rebooted` (prior boot's chain verified) / `owner_rebooted_unverified` (chain unverifiable or `instance_conflict`) | verified: confirmed absence → finalize attempt (`OWNER_RESTART`), then reconciliation or `expired`; unverified: finalize attempt (`OWNER_RESTART_UNVERIFIED`), execution quarantined `failed`, **no replacement spawn** |
  | winner of generation k crashed mid-write | `g<k>` dir, no readable claim.json (pending) | previous generation's state | pending-generation recovery: abandon marker, next generation appendable; no side effect can survive its crashed generation |
  | after fenced takeover | terminal `taken_over` generation record | `taken_over` | replacement path; the key can never spawn again |
- **Fenced stale-claim takeover (rev-4 dir-rename-away and rev-5 `.takeover`-lock shapes both withdrawn).** Rev 4 renamed the public claim dir away before publishing the replacement (an explicit `not_found` window). Rev 5 fixed the gap but introduced a *permanent* lock directory plus an in-place overwrite of `claim.json` — a lock that can strand if the winner crashes at the wrong point, and a stale-holder write path with a TOCTOU window (the round-5 blocker). Rev 6's takeover is simply **the next append to the generation log**: the same exclusive-create CAS, the same fence, no separate lock to strand or recover. A stale claim (current-boot claim older than the stuck threshold — 10 min — with no live registry entry for its key and no terminal job dir, or a prior-boot non-terminal claim classified dead by the verified container-lifetime chain below) is taken over as follows:
  1. **Append CAS**: the reclaimer exclusively creates the next generation dir `g<k+1>` (the shared mutation CAS). Exactly one reclaimer wins; losers get EEXIST, re-read the log (which now shows `taken_over` or is about to), and return the takeover response. If the loser's EEXIST was against a *different* mutator (e.g. a terminal write landed first), the loser re-reads and follows that state instead — the CAS never assumes who the other writer was.
  2. **State write**: the winner writes the full replacement claim `{...claim, state:"taken_over", generation: k+1, holder_boot_id: <this boot>, holder_uuid: <uuid>, taken_over_by_boot: <this boot>, taken_over_at: now()}` into `g<k+1>/claim.json` (temp+rename inside its own dir, fsync). The public digest path is never absent and never loses its marker: every reader sees either the previous complete generation or the complete `taken_over` generation. **Takeover is commit-then-cleanup**: once `g<k+1>/claim.json` exists, the postcondition is durable even if the winner crashes immediately after — there is no lock to recover and no in-place overwrite to redo.
  3. **Post-commit forensics (idempotent, retryable)**: the pre-takeover claim contents are already preserved by construction — the generation log *is* the forensic history; the sweep additionally copies the latest pre-takeover generation to `outputs/claims/.taken-<digest>-<uuid>` for convenience and renames any orphan `job_id` job dir the claim referenced to a quarantine dir (never deleted, never respawned). A takeover winner that crashes before forensics leaves the postcondition intact; the next boot's sweep redoes forensics idempotently (the quarantine rename is guarded by the dir no longer existing at its original path).
  - **Single postcondition, always**: the key at `<digest>` resolves to `taken_over` for authorized callers, continuously from the takeover commit onward, and `POST /models/run` replay for that key can never spawn — replay returns `{state:'taken_over'}` (410-equivalent). **Race closure, including the delayed-dispatcher interleaving (round-5 blocker)**: a dispatcher that appended a spawn record long ago, stalled past the stuck threshold, and wakes to spawn must first pass the **pre-spawn fence** (§2.2.4 claim primitive step 3c): it re-reads the log immediately before the side effect and finds generation `k+2` (`taken_over`) or a quarantined job dir — its record is no longer current, and it aborts without spawning. A concurrent *fresh publish* at the same digest fails with EEXIST at the staged-publish rename (the dir has existed since the original claim and is never removed), so a third dispatcher falls into the read path and sees `taken_over`. Within one boot the re-read is also unnecessary-but-mandatory belt-and-braces because the takeover sweep is boot-only and plumber is single-threaded (no in-process interleaving exists); across boots the fence is the mechanism. **At no interleaving can the old key be reclaimed and spawned.** The API-side replacement comes from the *reconciliation attempt*, which by construction has a **new** `attempt_key` (`attempt_no` incremented), so it is unaffected.
- **Verified boot-liveness / `owner_rebooted` classification (round-5 blocker 2: the R exit hook alone proves nothing under `SIGKILL`).** The exit hook (`run_server.R:311-336`) kills registry children only on a graceful stop. Rev 5 treated a prior boot's non-terminal claim as *provably* dead because of that hook — an assumption a hard parent kill voids. Rev 6 replaces the assumption with a **platform-enforced container-lifetime chain, self-verified at boot and announced**:
  - **The chain (topology, verified against source today).** The Plumber container's PID 1 is either docker-init (`init: true` on the service, `docker-compose.yml:107`) or the R process itself (compose files without `init:`, e.g. `docker-compose.prod.yml`, where `docker-entrypoint.sh` ends with `exec gosu sdm "$@"` — the exec chain leaves R as PID 1's direct child or as PID 1, with no in-container supervisor that could restart R in place). Model compute is a callr child of the R process (`models_helpers.R:227-259`) in the same PID namespace. Therefore **R-process death of any cause — graceful exit, runtime abort, `SIGKILL`, or the process being OOM-killed — terminates the container** (PID 1, or tini whose only child is R, exits), and **kernel teardown of the container's PID namespace kills every remaining process in it, including the callr child**. Container `stop`/`kill` similarly ends in namespace teardown. There is no mechanism by which a child survives into a later boot of the same container: a new boot exists only because the old container fully exited.
  - **Self-verification at boot (the guarantee is checked, not assumed).** At startup, before announcing, the boot computes its process chain from `/proc`: it records `pid_chain_verified: true` only if (i) `/proc/self/stat`'s PPid is 1, and (ii) PID 1's `/proc/1/comm` is this process itself (R as PID 1) or a known init supervisor (`docker-init`/`tini`). Any other chain — an unexpected wrapper shell, s6, supervisord, a restart-capable supervisor — yields `pid_chain_verified: false`. The announce (`POST /internal/instances/announce`, §2.3) carries `{instance_id, boot_id, api_base_url, announced_at, process_uptime, pid_chain_verified}`; `plumber_instance_boots` gains a `pid_chain_verified boolean not null default false` column (S1).
  - **API-side liveness conflict guard.** If two distinct boots of the same `instance_id` are simultaneously live (both sending `last_seen_at` heartbeats within the freshness window — possible only via a deployment misconfiguration running two containers with the same `SDM_PLUMBER_INSTANCE`), the API marks `instance_conflict` on that instance: prior-boot evidence for its claims is demoted to unverified for as long as the conflict persists, and the single-replica dispatch lock (§2.3) has already refused the duplicate. This is the live-evidence check for "the old boot might still be running" that the exit-hook assumption never had.
  - **Classification.** Resolve on a prior-boot non-terminal claim returns `owner_rebooted` (**confirmed absence**) only when the prior boot's row shows `pid_chain_verified: true` and no `instance_conflict` is active — in that case the container-lifetime chain proves the child cannot still be running, and the reconciler may finalize and allocate the reconciliation attempt. Otherwise resolve returns `owner_rebooted_unverified`: the reconciler finalizes the attempt (`OWNER_RESTART_UNVERIFIED`) and the execution `failed` (quarantined; explicit ops confirmation, e.g. from container tooling, is the only path to a retry — which is a fresh execution under §2.1 anyway). **Unknown is not permission to spawn; unverified absence is unknown.**
- **Spawn idempotency (replay distinguishes evidence; never acknowledges an unspawned job).** Replaying `POST /models/run` with the same `attempt_key`, after current-principal authorization in the API:
  - publish CAS lost + claim `state:'spawned'|'terminal'` **and** `job_id` **and** (live registry entry **or** terminal job dir) → `{replayed: true, job_id}` — spawn evidence confirmed;
  - claim with `job_id` but no registry entry and no terminal dir (`claimed_not_spawned` on the claim's own boot; `owner_rebooted`|`owner_rebooted_unverified` on any other boot, per the verified container-lifetime chain) → `{state: 'claimed_not_spawned'|'owner_rebooted'|'owner_rebooted_unverified', retry_after: <stuck threshold remainder>}` (429-equivalent for `claimed`; 410-equivalent dead evidence for both `owner_rebooted*` states) — **not** a successful replay; the child was never spawned, or is dead per the verified chain (invariant 14; unverified = unknown, quarantined, never a spawn license);
  - claim `state:'claimed'` (no `job_id`) or `taken_over` → `{state: 'claimed'|'taken_over', retry_after}` / 410-equivalent — never a second spawn;
  - unreadable claim → the defensive fail-closed path above.
  No response in any branch licenses the caller to treat an unspawned claim as a spawned job.
- **Resolve endpoint (internal-only; authorize before any disclosure; all partial states covered).** `GET /models/resolve?key=<attempt_key>` requires the internal token + a valid execution signature whose `execution_id` equals the claim's, plus a request-driven forwarded principal or the signed service actor (authorization model above). The API has already rechecked the requester's current project membership/action scope for the execution the key belongs to (or is the reconciler acting under its narrow scope). Plumber **authorizes before disclosing any state, for every claim state including partial ones**:
  - authorized, key resolves → `{present: bool, state: "running|completed|failed|claimed_not_spawned|claimed|owner_rebooted|owner_rebooted_unverified|taken_over", job_id: string|null}` — no config, no paths, no metrics;
  - key not found → `404 {"error": "Run not found"}`;
  - **signature/execution-id mismatch (a caller whose execution signature does not bind the claim's execution — e.g. a captured key presented under a different execution's credentials) → `404 {"error": "Run not found"}` — byte-identical to the not-found case**, disclosing neither `present` nor `state` nor `job_id`, for *every* claim state (claimed, claimed_not_spawned, owner_rebooted, taken_over, present, terminal). Foreign-project and removed/deleted-user probes never reach Plumber at all: the API-level current-principal/project recheck fails first and returns the same indistinguishable 404 shape with no Plumber call;
  - unauthenticated, missing internal token, missing execution signature, or neither a forwarded principal nor the signed service actor → `401` (plumber-auth-contract suite already pins this);
  - unreadable claim.json → `404 Run not found` for everyone (fail-closed above).
  Key unguessability (`nonce128`, below) is defense-in-depth, not the authorization boundary. The same current-principal check guards the replay branch of `POST /models/run`.
  - `attempt_key = idempotency_key || ':' || attempt_no` where `idempotency_key = sha256(canonicalExecutionJson({execution_id, payload_hash, run_seq, nonce128}))` and `nonce128` is the execution's one-time 128-bit random value (§2.2 schema).

### 2.3 Exact owner and process identity (the Plumber instance boot, not the worker)

Rev-1 error corrected: the BullMQ/Hono worker process cannot validate or route a kill of a child that lives in the Plumber container. Rev-2 error corrected: a single mutable `registry_era` column on `plumber_instances` destroys the prior era on update. The compute owner is the **Plumber instance boot**, persisted immutably.

- **Instance identity.** Each Plumber deployment has `SDM_PLUMBER_INSTANCE` (uuid, provisioned by compose/ops, stable across container recreation) and a **boot identity generated at process start**: `boot_id` = uuid4 generated in `run_server.R` startup. At boot, Plumber announces `POST /internal/instances/announce` with `{instance_id, boot_id, api_base_url, announced_at, process_uptime, pid_chain_verified}` (the self-verified `/proc` process-chain assertion of §2.2.4's container-lifetime chain; the boots table stores it). The API upserts `plumber_instances` (stable row) and inserts an append-only `plumber_instance_boots` row. Prior boots are never mutated (except `last_seen_at` heartbeats); a restart therefore never destroys the boot an attempt recorded. Boot ids are uuids, not clock-derived counters ("epoch seconds … incremented" from rev 2 is withdrawn): collisions are impossible and no monotonicity assumption is load-bearing — "greatest `announced_at`" is a routing hint only, and any mismatch is owner-gone.
- **Owner captured at acceptance, attempt-canonical.** `runModel`'s 200 response gains `owner: {instance_id, boot_id}` alongside `job_id` (the child PID is *not* returned; PID checks happen only inside the owner). Checkpoint B (§2.2.3 step 5) persists `owner_instance_id` + `owner_boot_id` on the **attempt only** (one-time write with `plumber_job_id`); executions carry no owner columns (§2.2). Every owner-addressed operation (cancel, status poll) reads the owner from the execution's open/last attempt — which may legitimately differ per attempt after a reconciliation dispatch on a new boot.
- **Wrong-era routing.** Any owner-addressed operation (cancel, status poll) is addressed to `(instance_id, boot_id)`. Before acting, the API verifies the attempt's `owner_boot_id` is still the instance's current boot (greatest `announced_at` in `plumber_instance_boots`); if not — or the announce target no longer exists — the operation returns `owner_gone` and the caller follows the fail-closed path. Inside Plumber, the registry is process-local, so any request that arrives at the wrong boot is simply absent from the registry; there is no cross-boot aliasing.
- **Reaching the exact owner.** Single-Plumber-replica (the current deployment and P2-10's limit): one row, `api_base_url` is the service address; cancel/status land on the right process trivially, and the boot check above catches a restarted process. When a second replica ever exists, `api_base_url` must be per-instance reachable (headless service / instance port); the announce already carries an address that routes to *that* process, so the multi-replica exit is a deployment change plus the load test, not a protocol change. The dispatch lock (below) still enforces one *dispatching* worker regardless.
- **Verification inside the owner's namespace.** All process-targeted verification happens *inside Plumber*: `sdm_cancel_pid_first` (`plumber_helpers.R:151-186`) resolves the child only via the in-process registry (`sdm_registry_get(job_id)`), which is inherently namespace-correct. **Complete PID-authority removal for model jobs (rev-2 inventory extended to all four authorities):**
  1. cancel fallback `meta$process_pid` (`plumber_helpers.R:174-183`) — removed;
  2. model cancel's direct `sdm_kill_pid(meta$process_pid)` (`models_helpers.R:1345-1347`) — removed; `killed` is true only via the registry handle;
  3. model status liveness probe `pskill(meta$process_pid, 0)` (`models_helpers.R:809-813`) — removed; status for a `running` meta with no registry entry is derived from the job dir only (meta terminal status) and the API reconciler's adoption path; post-restart "running" jobs are exactly the adopted-by-probe population, never PID-guessed;
  4. the shutdown sweep over job-dir `meta.json` PIDs (`run_server.R:340-355`) — removed for model jobs; shutdown kills registry children only (the registry sweep at `:311-336` stays), and children whose registry entries are gone are left to the API reconciler's key-probe adoption plus the existing 24h `orphan_cleanup` stale-running marking (`run_server.R:263-300`).
  The equal-PID problem disappears because no PID crosses any boundary at all; Hono addresses an instance boot, and the instance checks its own registry.
- **Fail-closed.** If the registry entry for `plumber_job_id` is gone (boot advanced, process died, key mismatch): cancel returns `{"killed": false, "reason": "owner_gone"}`; the execution is finalized `cancelled` if the job dir confirms a terminal state, else the reconciler treats it as `lost_response`-equivalent and key-probes (§2.2.3 step 6). **No PID is read, probed, or killed for model jobs anywhere — Hono, Plumber status, Plumber cancel, or Plumber shutdown.** Climate/covariate download jobs keep the PID fallback *temporarily* with a start-tick check added in Plumber (`/proc/<pid>/stat` field 22 compared to a `process_start_ticks` recorded in their meta at spawn), until they adopt this contract (§8.4).
- **Queue-worker identity** is still registered (worker bookkeeping for leases/heartbeats and the single-replica lock, not referenced by cancel). The single-replica dispatch invariant is enforced: the worker takes a Postgres advisory lock `sdm:dispatch:<queue>` at boot; a second live instance logs and refuses to dispatch. Exit from single-replica (P2-10) requires the green test matrix in §6 first.

### 2.4 Authorized retry and cancellation

- `POST /runs/:id/retry`: project member retry of a run whose latest execution is terminal `failed|cancelled|expired` (and whose inputs still resolve; §2.2.1 reservation-time sealing applies to the new execution). Reserves a **new execution** (§2.1) with a fresh `nonce128`/`idempotency_key` and `retry_of_execution_id` set. A retry while a non-terminal execution exists is refused `409`; a retry of a `lost_response` execution is refused `409` (the reconciler owns that state) — "unknown is not permission to spawn".
- `POST /runs/:id/cancel`: **durable intent first, orthogonal to status** (rev-2 blocker-1 fix). **The reserved case is a direct terminal CAS — it never passes through `cancel_requested` (rev-4 shape withdrawn; there is no legal `reserved → cancel_requested` transition and no attempt exists to finalize).** The cancel handler runs exactly two candidate transactions, in order, each a CAS on the pre-state it reads:
  1. **Reserved-direct CAS (one transaction):** `UPDATE executions SET status='cancelled', cancel_requested_at=now(), finalized_at=now() WHERE id=? AND status='reserved' AND finalized_at IS NULL RETURNING status;`
     - **Row returned** → the cancel won before any dispatch. **No attempt exists in the `reserved` state** (attempts are created only by the dispatch CAS, §2.2.3 step 2), so **no attempt is created and none is finalized**; `attempt_count` stays 0 and `execution_attempts` is empty for this execution. The only effect after commit is the idempotent BullMQ job removal (post-commit effect, below). A worker that subsequently picks up the BullMQ job cannot spawn: its dispatch CAS (`WHERE status='reserved'`) affects zero rows, and the worker then exits without a Plumber call — checkpoint A also re-reads and sees the terminal state.
     - **Zero rows** → the execution was already past `reserved` (the dispatch CAS won) or terminal; fall through to transaction 2 with a fresh read.
  2. **Durable-intent transaction (for every non-terminal, non-reserved execution):** `UPDATE executions SET cancel_requested_at = now(), status = CASE WHEN status='dispatching' THEN 'cancel_requested' ELSE status END WHERE id=? AND finalized_at IS NULL AND status <> 'reserved' RETURNING status, cancel_requested_at;` — `cancel_requested` is reachable **only from `dispatching`**; `accepted|adopted|lost_response` keep their status and gain the durable intent column. Zero rows → terminal already → `409`. `cancel_requested_at`, once set, is never cleared by any transition; every terminal path checks it (below).
  - `reserved` → handled entirely by the reserved-direct CAS above (transaction 1); no separate per-state branch exists. For completeness of the ordering argument: the queue removal is *not* in the same transaction as the CAS (queue state is not transactional with PostgreSQL); ordering is safe because the execution CAS is what prevents any dispatch — a worker that picks the BullMQ job up after the cancel either sees the finalized execution at checkpoint A (no Plumber call) or loses its dispatch CAS. A duplicate job removal is harmless; a lost removal is harmless for the same reason.
  - `dispatching` (now `cancel_requested`) → the worker is between checkpoints. Three sub-cases, all closed by the key protocol and the durable intent:
    - *cancel before checkpoint A*: worker sees `cancel_requested`/`cancel_requested_at`, never calls Plumber (§2.2.3 step 3).
    - *cancel during the Plumber call (in-flight or response lost)*: worker at checkpoint B CASes to `accepted` keeping `cancel_requested_at` set and immediately routes cancel (child adopted then killed). If the worker got no response it sets `lost_response` — **with `cancel_requested_at` still set** — and the reconciler's probe path (§2.2.3 step 6a) adopts the child and routes cancel to the owner before any other action. If the worker died entirely, the reconciler probe path does the same. Every successful spawn is discoverable by `attempt_key`, and every adopted child of an execution with `cancel_requested_at` set is cancelled before that execution can finalize in any non-`cancelled` state; **no spawned child can be orphaned and no intent can be erased**.
    - *cancel after accept*: normal owner-routed cancel.
  - `accepted|adopted` → route cancel to the verified owner boot (§2.3), which kills via registry only and returns `killed`/`owner_gone`. Plumber verifies the registry entry matches the `job_id` and the current principal before killing; the Redis cooperative cancel flag stays keyed by `plumber_job_id` (TTL semantics unchanged, `redis.R:98-106`). Execution finalizes `cancelled` once the owner confirms kill or owner-gone-with-terminal-job-dir; `owner_gone` with no confirmation follows the `lost_response` key-probe path (which respects `cancel_requested_at`) before finalizing.
  - `lost_response` → the probe path of §2.2.3 step 6 runs *with the durable cancel intent applied*: adopt-then-cancel if present; confirmed-absent (no claim) → finalize execution `cancelled` directly (intent recorded, nothing to kill); claimed/stale-claim → takeover, then `cancelled` once absence is confirmed.
- **Terminal-state guard.** The single transition function refuses to finalize any execution in `succeeded|failed|expired` while `cancel_requested_at IS NOT NULL` unless a confirmed-absent probe (or owner-confirmed kill) is on record for its open/last attempt. `cancel_requested_at` is never cleared — it stays as history.
- Hono's `runs.status` mirrors terminal/non-terminal state only via the projection function.
- Batch cancel (`sdm-batch.ts:103+`) becomes a loop over the same per-execution cancel with per-run authorization, not a bulk status UPDATE.
- Concurrent cancel-vs-dispatch is a state-machine impossibility rather than a hope: the only path to `accepted` CASes *from* `dispatching` or `cancel_requested` and preserves `cancel_requested_at`; the only paths to `cancelled` are the reserved-direct CAS (§2.4 transaction 1, from `reserved` before any attempt exists), the durable intent with confirmation, or terminal confirmation. Integration gate: test 8b (§6).

### 2.5 Restart reconciliation

On boot, and every sweep, for every non-terminal execution:

- `accepted|adopted` → poll status **through the owner boot recorded on the open attempt** (attempt's `owner_instance_id` + `owner_boot_id` + `plumber_job_id`); boot mismatch, instance gone, or Plumber `owner_gone` → key-probe by `attempt_key`. **The probe can return only terminal or dead evidence for another boot's child — a running child is live only on its spawning boot (invariant 14), so "resume owner-routed polling through the current boot" is impossible and removed (rev-4 wording withdrawn).** Probe outcomes: terminal-present → adopt identity if missing, project the observed outcome, finalize (respecting `cancel_requested_at`, §2.4 terminal-state guard); confirmed absent (`not_found`, `taken_over`, or verified `owner_rebooted` — non-terminal evidence on a non-owning boot is proof of death only under the §2.2.4 verified container-lifetime chain; unverified evidence yields `owner_rebooted_unverified` and the quarantined path with **no replacement attempt**) → the explicit `accepted|adopted → lost_response` transition of §2.2.3 step 6 (finalize open attempt `outcome='unknown', error_code='OWNER_GONE'` — `OWNER_RESTART` where the container-lifetime chain is the cause — CAS status, then reconciliation attempt or `expired` per budget). The finalized attempt's owner snapshot is never rewritten (invariant 12); a replacement attempt, if budgeted, is dispatched fresh on the current boot and records its own snapshot. The attempt's persisted `owner_boot_id` still points at the immutable prior boot row; the test matrix (§6 test 9) asserts the second poll uses the *attempt's* recorded owner and never rewrites it.
- `lost_response` → key-probe **the open attempt first** (§2.2.3 step 6): present → adopt (one-time identity write on the open attempt) then observe/cancel per intent; confirmed absent → finalize the open attempt as `unknown/LOST_RESPONSE`, then the single reconciliation attempt or `expired` per budget; claimed/stale → takeover path.
- `reserved|dispatching|cancel_requested` with expired lease and no confirmed Plumber job → per §2.2.3 step 6 (`cancel_requested`/`cancel_requested_at` finalizes `cancelled`, others get the one reconciliation attempt or `expired`). A `dispatching` execution with an expired lease is probed by its open attempt's key before any replacement is allocated — the child may exist.
- Owner heartbeat: the polling loop touches `executions.lease_expires_at` and `plumber_instances.last_seen_at` / `plumber_instance_boots.last_seen_at`. The lease is observational; it never authorizes spawn by itself.
- Idempotency-request housekeeping: null `response_body` past `expires_at + 7d`; **delete nothing** (tombstones persist, §2.2.2).
- Stale-claim housekeeping (Plumber side, `orphan_cleanup` extension): claims past the stuck threshold with no registry entry are takeover-eligible; the takeover protocol (§2.2.4) makes the sweep safe to run concurrently with itself and with dispatch.

Legacy runs with no execution row keep the current sweep paths untouched during migration (§5 rollout); the ownerless `parentRunId` skip (`plumber-sync.ts:150-162`) is unchanged until the input-lineage decision in §8 is made.

- `execution_events` gives every durable transition a stable `(execution_id, seq)`. The SSE/WebSocket layer emits transitions with `(runId, executionId, seq)`; progress (percent/logs/stage) remains fire-and-forget pub/sub and is explicitly labeled ephemeral. ## 3. State transitions (execution)

```
reserved ──dispatch CAS──▶ dispatching ──200+owner──▶ accepted ──terminal poll──▶ succeeded|failed|cancelled
   │                          │   ▲
   │                          │   └──── cancel_requested ──200+owner──▶ accepted (intent kept; adopt-then-cancel)
   │                          └──transport err──▶ lost_response ──probe: present──▶ adopted ──┐
   │                                                     └─probe: confirmed absence (not_found|taken_over|owner_rebooted-verified)──▶ (finalize open attempt; CAS lost_response→dispatching, one reconciliation attempt; unverified owner_rebooted → quarantined failed, no replacement)
accepted|adopted ──owner_gone + probe: confirmed absence──▶ (finalize open attempt; CAS accepted|adopted→lost_response) ──▶ reconciliation attempt | expired
   │
   ├─reserved-direct cancel CAS (no attempt exists)──▶ cancelled
   └─owner-routed cancel──▶ cancelled
dispatching ──cancel intent CAS──▶ cancel_requested ──(no spawn, checkpoint A)──▶ cancelled
cancel_requested ──(probe confirms child)──▶ adopted → cancelled
reserved|dispatching with expired lease, no job, budget spent ──▶ expired
```

`cancel_requested_at` (durable, orthogonal) is set on any non-terminal execution by cancel and is preserved by every transition above; it is read by checkpoint A, checkpoint B, the reconciler probe path, and the terminal-state guard. Transitions not drawn are illegal; the state-machine unit test table-walks all of them, including the `cancel_requested_at`-preservation property per transition and the `accepted|adopted → lost_response` owner-loss path.

Invariants:

1. One non-terminal execution per run (partial unique index on `executions(run_id) WHERE finalized_at IS NULL`).
2. `attempt_no` is gapless per execution (= `attempt_count` from the dispatch CAS) and append-only; `execution_attempts` rows are never updated after `finalized_at`, and the only pre-finalization writes are the one-time `plumber_job_id`/`owner_instance_id`/`owner_boot_id` (checkpoint B or probe adoption) and the finalization write of `outcome/error_*`. The probe-adoption write happens **only while the attempt is open** — a finalized attempt is immutable.
3. `plumber_job_id` is written at most once per **attempt** and is unique across attempts; an execution may legitimately carry different job ids across its attempts. **Executions carry no owner or job columns**: ownership is attempt-canonical, and there is no execution-level write-once owner to contradict.
4. For every non-final attempt, either the attempt key resolves in Plumber to one of the crash-point table's persisted states, or the claim is takeover-eligible; a spawned child always has a discoverable claim (invariant for cancel-safety).
5. `runs.status` is written only by the projection of execution terminal/non-terminal state (single function, single file).
6. No code path spawns compute without a prior dispatch CAS win on a durable row (`reserved→dispatching` or `lost_response→dispatching` for the one reconciliation attempt).
7. Cancel and retry are durable state changes first; their side effects are idempotent (key claim) or owner-verified (registry kill). `cancel_requested_at`, once set, is never cleared and is honored by every finalization path (terminal-state guard). Queue (BullMQ) removal is an idempotent post-commit effect, never part of a PostgreSQL transaction.
8. No PID is read, recorded, probed, or killed for model jobs anywhere — Hono, Plumber status, Plumber cancel, or Plumber shutdown. Process identity is `(plumber_instance_id, boot_id, job_id)` verified inside Plumber's namespace via its process-local registry.
9. A replayed `(principal, idempotency-key)` pair can create at most one run and one execution, ever (PK on `idempotency_requests` + permanent tombstone, no deletion path). The reservation transaction is executable as written: pre-allocated run UUID, `ON CONFLICT DO NOTHING` winner proof via `RETURNING`, deferrable FK satisfied at commit.
10. Terminal executions are never reopened; retry creates a new execution linked by `retry_of_execution_id`.
11. Every claim-bound Plumber call is internal-only (service token + execution-key signature binding the exact `execution_id` + a request-driven forwarded principal or the signed service actor). The API rechecks the current requester's project membership/action scope against the execution's `project_id` before every request-driven call — any current project member with action scope passes, not just the historical owner; foreign/removed/deleted requesters get an indistinguishable 404 at the API with no Plumber call. The service reconciler is a distinct narrowly scoped actor: observe/cancel on the bound execution only, never dispatch/spawn. The claim's `owner_user_id` is audit provenance, not an authorization check; key possession alone (without the execution signature) authorizes nothing.
12. An attempt's owner snapshot is immutable after checkpoint B / probe adoption: `(owner_instance_id, owner_boot_id)` on the attempt is written once, and `plumber_instance_boots` rows are append-only (no era destruction). Any execution-level owner is an explicitly mutable derived projection (latest open attempt's owner) and is never stored or routed through. There is no cross-boot ownership transfer: a replacement attempt records its own snapshot; a finalized attempt's snapshot is never rewritten.
13. Dispatch is authorized twice: at reservation (reservation-time sealing, §2.2.1) and **immediately before spawn** (principal, membership, asset identity, payload-hash revalidation, §2.2.3 step 3). A revocation, deletion, or mutation between the two denies the dispatch; sealed locators never authorize a spawn by themselves.
14. **Verified boot-liveness invariant (rev 6: the exit-hook-only form is withdrawn).** A model child is live only while the container whose PID namespace holds it is running: the Plumber container's PID 1 is either docker-init/tini (`init: true`, `docker-compose.yml:107`) with R as its only child (`docker-entrypoint.sh` ends `exec gosu sdm "$@"`), or R itself (compose files without `init:`); a callr child (`models_helpers.R:227-259`) shares the namespace, so R-process death of *any* cause, and container stop/kill, all end in kernel teardown that kills the child — and a new boot of the same instance implies the old container fully exited. This guarantee is **checked, not assumed**: each boot self-verifies its `/proc` process chain and announces `pid_chain_verified` (§2.2.4), and the API's `instance_conflict` guard demotes evidence while two boots of one instance are simultaneously live. Running-present key-probe evidence can only be returned by the owning boot; non-terminal claim evidence observed on another boot is confirmed absence **only when the prior boot announced a verified chain and no conflict is active** (`owner_rebooted`); otherwise it is `owner_rebooted_unverified` — quarantined, never a replacement-spawn license. No design path transfers, adopts-across-boots, or re-polls another boot's running child; absence is resolved by finalization plus a fresh reconciliation attempt that records its own owner snapshot.
15. **Fenced claim-log invariant.** Every mutation of a claim is an append to its generation log (`g<k>` exclusive create = the CAS; content written only by the winner inside its own generation dir; readers take the highest readable generation). No `claim.json` is ever overwritten in place and no lock file exists. Any spawn must pass the pre-spawn fence: re-read the log immediately before the side effect and prove the current generation is the spawner's own spawn record. A claim can therefore never be double-spawned at any interleaving; crashed mutations are recovered by pending-generation abandonment, never by overwriting a winner.
16. **Reserved-cancel invariant.** `cancel_requested` is reachable only from `dispatching`; a `reserved` execution is cancelled by a direct `reserved → cancelled` CAS in one transaction, and because no attempt exists before the dispatch CAS, a reserved-cancel creates and finalizes no attempt (`attempt_count` stays 0). No transaction ever CASes on a status value it has already replaced.

## 4. Alternatives rejected

- **Redis as the ownership registry.** Rejected: architecture already fixes Postgres as authoritative for queue/lifecycle records (`docs/ARCHITECTURE.md:39`); Redis is transport and loses state on flush/restart, which is precisely the failure class P2-10 tests.
- **BullMQ `attempts` as the retry mechanism.** Rejected: the worker holds the job active for hours of polling; a "retry" replays the whole side-effecting handler with no durable attempt record, which is the current bug (`queue.ts:244-291`). Retries become DB executions/attempts; BullMQ carries at most one dispatch per attempt with `attempts: 1`.
- **Reopening a terminal execution for retry (rev-1 shape).** Rejected in rev 2, retained: it contradicts write-once `plumber_job_id` and append-only finalization, and rewrites history a user may already have seen.
- **Finalizing the open attempt before probing (rev-2 shape).** Rejected in rev 3: a present job belongs to the open attempt, and invariant 2 forbids writing identity onto a finalized attempt — the probe must come first, adoption writes the open attempt, and only confirmed absence justifies finalization-then-replacement. Finalizing first makes adoption unimplementable and leaves a live child untracked.
- **Cancel intent as status only (rev-2 shape).** Rejected in rev 3: a transition to `lost_response` or `adopted` would erase the fact that an adopted child must die. `cancel_requested_at` is an orthogonal durable column preserved by every transition.
- **`SELECT ... FOR UPDATE` on a missing idempotency row (rev-2 shape).** Rejected in rev 3: row locks do not serialize inserts of absent rows; the conflict-safe `ON CONFLICT DO NOTHING` reservation is the only exactly-once primitive here.
- **Deleting idempotency-request rows after retention (rev-2 shape).** Rejected in rev 3: deletion re-opens the one-key/one-execution gate after housekeeping. Permanent tombstones; only `response_body` is pruned.
- **Claim `mkdir` + separately-written `claim.json` with overwrite reclaim (rev-2 shape).** Rejected in rev 3: a concurrent loser can observe a partial/missing file, and overwrite reclaim lets two reconcilers both spawn. Atomic rename for the file, atomic dir-rename takeover for stale claims.
- **Mutable `registry_era` column on `plumber_instances` (rev-2 shape).** Rejected in rev 3: the update destroys the era an attempt recorded. Append-only boot rows with uuid boot ids; ordering is a hint, mismatch is owner-gone.
- **Key possession as resolve authorization (rev-2 shape).** Rejected in rev 3: an unguessable key is not an authorization model, and captured keys must not disclose state. Current-principal verification, byte-identical 404 for foreign keys.
- **Historical-owner binding without current-principal rechecks, and direct API-key resolve (rev-3 shape).** Rejected in rev 4: binding a claim to the principal that happened to reserve it, without rechecking current project membership/action scope at resolve/replay/poll/cancel/dispatch time, violates the authorization boundary (`AGENTS.md:30-36`) and is weaker than the existing worker, which re-resolves principal/assets immediately before dispatch (`queue-model-worker.ts:27-31`). Rev 4 makes claim-bound Plumber endpoints internal-only (service token + execution signature + forwarded principal) and rechecks current authorization in the API before every call.
- **Public `mkdir` publication before owner metadata exists, and ambiguous takeover postconditions (rev-3 shape).** Rejected in rev 4: a public claim dir without a readable, owner-bound `claim.json` gives resolve nothing to authorize against and leaks an incomplete state's existence. Staged private claim + one atomic publish rename; takeover ends in exactly one state (`taken_over` terminal claim, key never spawnable again).
- **Replay acknowledging `claimed_not_spawned` as a spawned job (rev-3 shape).** Rejected in rev 4: a recorded `job_id` alone is not spawn evidence; replay must confirm registry entry or terminal dir before returning `{replayed: true}`.
- **Execution-level write-once owner columns (rev-3 shape).** Rejected in rev 4: checkpoint B's per-acceptance update contradicted the write-once claim, and owner-restart reconciliation on a new boot would have had to overwrite it. Ownership is attempt-canonical; any execution owner is a derived, explicitly mutable projection that is never stored.
- **BullMQ job removal "in the same transaction" as the PostgreSQL cancel CAS (rev-3 shape).** Rejected in rev 4: queue state is not transactional with PostgreSQL. Durable cancel commits first; queue removal is an idempotent post-commit effect; the DB CAS is what prevents spawn.
- **Reservation-time payload sealing only (rev-3 shape).** Rejected in rev 4: sealing without an immediate-before-spawn revalidation lets a revocation, deletion, quarantine, or byte mutation between reservation and dispatch spawn from stale locators. Dispatch is authorized twice (invariant 13).
- **Renaming the public claim dir away during takeover, then republishing (rev-4 shape).** Rejected in rev 5: the gap between rename-away and replacement publish is an explicit `not_found` window in which a concurrent dispatcher wins the publish CAS at the old digest and spawns. Rev 6 replaces the whole mechanism (below).
- **Permanent `.takeover` lock dir + in-place atomic `claim.json` replacement (rev-5 shape).** Rejected in rev 6 (round-5 blocker): the lock has no release, so a takeover winner that crashes between lock create and claim replacement leaves the claim permanently takeover-locked with no recovery path that cannot itself strand; the in-place overwrite has a check-then-write window in which a stale dispatcher that passed the generation check can still overwrite a newer claim (classic ABA/TOCTOU on a shared mutable file); and a delayed dispatcher that read the claim before stalling could spawn after takeover with nothing re-checking generation at the moment of the side effect. The fenced generation log (exclusive next-generation create as the shared CAS for every mutation, plus the mandatory pre-spawn fence re-read) has none of these: no lock to strand (the append *is* the commitment), no overwrite (append-only), and stale holders lose deterministically at EEXIST.
- **`owner_rebooted` as confirmed absence licensed by the R exit hook alone (rev-5 shape).** Rejected in rev 6 (round-5 blocker): `pr_hook("exit")` runs only on graceful shutdown; a `SIGKILL`ed, aborted, or OOM-killed parent runs no hook at all, so hook-based reasoning proves nothing about the child in exactly the hard-death cases that matter. Confirmed absence now requires the platform-enforced container-lifetime chain (PID 1 = init/tini-with-R-as-only-child or R itself; kernel namespace teardown kills the callr child on any process or container death), which is self-verified at boot via `/proc` and announced (`pid_chain_verified`), with an API-side dual-boot `instance_conflict` guard as live evidence. Unverifiable chains yield `owner_rebooted_unverified` — quarantined, never a spawn license.
- **`reserved → cancel_requested` followed by a `WHERE status='reserved'` finalize (rev-4 shape).** Rejected in rev 5: the second transaction CASes a state the first already replaced (always zero rows), and a reserved execution has no attempt to finalize. Reserved-cancel is one direct `reserved → cancelled` CAS; `cancel_requested` is reachable only from `dispatching`.
- **Historical claim-owner equality (or admin bypass) as Plumber's authorization model (rev-4 shape).** Rejected in rev 5: it cannot authorize a current non-owner project collaborator, and it leaves no legal principal for reconciling an execution whose reserving user was deleted. Plumber never derives project authorization (no membership data); the API's current-principal/project recheck authorizes request-driven calls, and a signed, narrowly scoped service actor (observe/cancel only, never dispatch) handles owner-deleted reconciliation.
- **Cross-boot owner transfer / "resume polling through the current boot" (rev-4 wording).** Rejected in rev 5 and retained: the registry is process-local and a running child of a prior boot cannot exist on the current boot (verified container-lifetime chain, invariant 14). Non-terminal evidence after a boot change is classified per that chain (`owner_rebooted` when verified, `owner_rebooted_unverified` quarantined otherwise); recovery is finalize-plus-fresh-reconciliation-attempt with its own owner snapshot, never a rewrite of the immutable attempt snapshot (invariant 12/14).
- **Attempt columns on `runs`.** Rejected: run is scientific lineage; attempts are dispatch facts with append-only semantics and per-attempt external identity.
- **Plumber writing execution state to Postgres.** Rejected: Plumber is the compute boundary, not a state owner (`docs/ARCHITECTURE.md:22`); giving it DB credentials widens the blast radius of the R runtime. Its contract is the atomic key claim plus the authorized key-scoped read-only resolve.
- **PID-verified ownership anywhere (status, cancel, or shutdown).** Rejected: host PIDs are invisible/unreliable across containers (P2-10 equal-PID test). No PID crosses any boundary for model jobs; the owner boot checks its own registry, status derives from the job dir, shutdown kills registry children only.
- **Event-sourcing all progress into Postgres.** Rejected: progress volume (5s polls, rotating 5MB JSONL in the child, `run_model_background.R:96-102`) would turn telemetry into the primary write load. Durable transitions only; progress stays ephemeral.
- **Config-hash submission dedupe at enqueue (current behavior).** Rejected as currently implemented (failure 1.2.5): the dedupe key must include run identity. Intentional duplicate *submissions* remain a product decision (§8.2); accidental replays are covered by request idempotency (§2.2.2), not by config hashing.
- **Deriving request idempotency from server-generated run ids (rev-1 shape).** Rejected: a key derived from the newly created run id cannot deduplicate a replay whose first response was lost. Request keys must originate with the client's logical submit.
- **Payload hash over resolved filesystem paths (rev-1 shape).** Rejected: paths are mutable locators. Identity uses the already-existing `content_sha256`, revalidated at reservation.

## 5. Rollout and rollback

- Phase A (inert schema): migration adds the tables and indexes (`executions`, `execution_attempts`, `idempotency_requests`, `plumber_instances`, `plumber_instance_boots`, `execution_events`; no asset columns — `content_sha256` already exists). No behavior change. Rollback: drop tables.
- Phase B (dual-write behind `SDM_DURABLE_EXECUTION` flag): worker writes executions and attempts while existing run-status writes continue; reconciler runs in shadow mode (logs what it would do). Plumber claim/resolve/announce endpoints ship additive (claim is a no-op wrap for unkeyed callers during B; announce is accepted and recorded but not yet authoritative). Request idempotency middleware ships accepting-but-not-requiring the header. Rollback: flag off; tables remain but unused.
- Phase C (switch): projection owns `runs.status`; BullMQ `attempts: 1`; string-matched re-throw removed; cancel/retry use the CAS paths with durable `cancel_requested_at`; boot-based owner capture enforced (missing `owner` in response fails the dispatch → `lost_response`); shadow reconciler becomes authoritative; all four model-job PID authorities removed (cancel fallback, direct kill, status liveness probe, shutdown sweep). Legacy sweeps (stuck-queued 5-min, 2h stalled, 404-streak) retained and additionally keyed on executions. Rollback: flag off (revert to Phase B behavior); PID-authority restoration is a Plumber config/code revert.
- Phase D (cleanup, separate PR): remove legacy sweep paths; delete dead columns only after a full migration cycle proves execution lineage coverage.
- Targets: P2-09 keeps Targets/batch unavailable; when its lifecycle PR lands, Targets jobs adopt this same contract (the `targets-` job id branch in `plumber-sync.ts:165-167` migrates like model jobs).

## 8. Unresolved decisions requiring Pacey

1. **Sync (non-async) run path.** It bypasses the queue and writes `running` before dispatch (`sdm-runs.ts:159-221`). Recommendation: route it through the same execution reservation (identical code path, just awaited) and keep the API shape. Decision: keep sync mode at all?
2. **Duplicate-submit suppression.** Current config-hash dedupe accidentally drops the second run (1.2.5). Under the new model, identical configs create two runs by default; request idempotency covers accidental replays only. Do you want explicit submit-level dedupe ("you already have a queued run with this config") as UX, or always run both?
3. **Legacy runs without execution lineage** (including ownerless `parentRunId`-less running rows, `plumber-sync.ts:150-162`): backfill synthetic executions, or leave them on legacy sweeps until natural expiry? Backfill cost is one migration pass.
4. **Scope of the first contract PR.** Model jobs only (recommendation: yes; climate/covariate/clean adopt it in a follow-up, keeping their PID fallback + start-tick check meanwhile), or all job types at once? Note the shutdown-sweep removal (§2.3 item 4) removes meta-PID killing for model-job dirs while download jobs keep registry-based kills and their temporary checked fallback.
5. **Reconciliation budget.** How many reconciliation attempts before `expired` for a `reserved` execution that never confirmed a Plumber job? Proposal: 1; then `WORKER_ORPHAN`-equivalent failure with a clear hint. Affects UX for flaky-Plumber deployments.
6. **Cancel-key TTL** stays 1h (`redis.R:103`)? Under execution CAS the flag is cooperative only, so a longer TTL is harmless but delays nothing; confirm 1h is acceptable.
7. **Idempotency-key mandatory or optional** for API clients other than the reference UI (curl/script users)? Proposal: optional server-side, mandatory in the UI, revisit after one release. Note the permanent-tombstone storage model: rows accumulate one per keyed submit; volume is trivially small relative to runs.
8. **Instance announce trust model.** `POST /internal/instances/announce` is internal-network + service-token only (compose network). Confirm Plumber's instance uuid is provisioned via env in compose and never auto-generated at boot (auto-generation would break identity stability across container recreation), and that boot ids may be process-generated uuid4 (they are per-process-start identity only).
9. **Quarantine retention.** Stale-claim takeover quarantines orphan job dirs rather than deleting them. Confirm a retention window (proposal: same 7d failed-retention as `orphan_cleanup`, `run_server.R:267`) and that ops accepts quarantine dirs under `outputs/jobs/.quarantine`.
10. **Deployment topology precondition for the verified boot-liveness chain (new in rev 6).** The `owner_rebooted` confirmed-absence classification rests on the container-lifetime chain: Plumber runs in one container whose PID 1 is docker-init/tini (`init: true`, `docker-compose.yml:107`) with R as its only child, or R itself (`docker-compose.prod.yml` has no `init:`; `docker-entrypoint.sh` ends `exec gosu sdm "$@"`), and **no in-container supervisor may ever be introduced that can restart R in place** (supervisord, s6, a wrapping shell with restart logic). The boot-time `/proc` self-check makes violations *detectable* (`pid_chain_verified: false` → quarantined, no auto-spawn), but a standing violation would turn every restart into an ops-confirmed recovery. Confirm: (a) all deployment variants (dev, base, prod images) keep this topology; (b) `init: true` is added to prod if the prod image relies on tini, or accepted that R is PID 1 there; (c) the `/proc/1/comm` allow-list (init, docker-init, tini) is acceptable as the supervisor whitelist.

## 9. What this design deliberately does not do

- No multi-replica claim. The advisory lock makes the single-dispatch limit enforced, and P2-10's exit criteria stay in force.
- No Targets enablement (P2-09), no batch execution availability change.
- No provenance/immutable-output work (separate ROADMAP gates).
- No event sourcing of progress, no new telemetry.
